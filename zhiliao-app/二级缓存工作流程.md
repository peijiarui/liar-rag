# 两级缓存（Two-Tier Cache）工作流程

## 一、涉及的类和模块

| 类 | 所属模块 | 角色 |
|------|----------|------|
| `CacheConfig` | `zhiliao-app` | **组装车间**：声明所有缓存相关 Bean |
| `TwoTierCacheManager` | `zhiliao-app` | **代理经理**：实现 `CacheManager`，对外提供两级缓存 |
| `TwoTierCache` | `zhiliao-app` | **实际执行者**：实现 `Cache`，内部持有 L1 Caffeine + L2 Redis |
| `RetrievalCacheService` | `zhiliao-retrieval` | **调用方**：标注 `@Cacheable`/`@CachePut`/`@CacheEvict`，声明式使用缓存 |

## 二、类的关联方式（Spring Cache 抽象）

这几个类表面上没有直接引用关系，连接的"胶水"是 **Spring 缓存 AOP 机制**：

```
@EnableCaching                    ← 在 CacheConfig 上，开启 Spring 缓存能力
       ↓
Spring 扫描 @Cacheable/@CachePut  ← 在 RetrievalCacheService 上
       ↓
为 RetrievalCacheService 创建 AOP 动态代理
       ↓
AOP 拦截器需要找一个 CacheManager
       ↓
找到 @Primary 的 twoTierCacheManager  ← TwoTierCacheManager（声明在 CacheConfig 中）
       ↓
按缓存名 "retrieval_result" 获取 Cache 实例    ← TwoTierCache（由 TwoTierCacheManager 内部创建）
       ↓
调用 Cache.get(key) / Cache.put(key, value)
       ↓
内部路由到 L1 CaffeineCache 或 L2 RedisCache
```

**核心思想：** `RetrievalCacheService` 只需要写一行 `@Cacheable("retrieval_result")`，Spring 框架在运行时自动串联起 `TwoTierCacheManager` → `TwoTierCache` → L1/L2 的全链路。这就是**声明式缓存**——只声明规则，框架负责路由。

## 三、读缓存流程：getCachedRetrieval("请假流程", "1_2")

```
RetrievalCacheService.getCachedRetrieval("请假流程", "1_2")
  │  @Cacheable(value = "retrieval_result", key = "#canonicalQuery + ':' + #deptSuffix")
  │
  ▼
[Spring CacheInterceptor（AOP 代理拦截）]
  │  计算 key = "请假流程:1_2"
  │  找到 @Primary CacheManager → TwoTierCacheManager
  │  获取缓存区 "retrieval_result" → TwoTierCacheManager.getCache("retrieval_result")
  │                               │
  │                               ├─ l1.getCache("retrieval_result") → CaffeineCache
  │                               └─ l2.getCache("retrieval_result") → RedisCache
  │                               └─ 返回 new TwoTierCache("retrieval_result", Caffeine, Redis)
  │
  ▼
TwoTierCache.get("请假流程:1_2")                        ← TwoTierCache.java:38
  │
  ├─ 1️⃣ l1.get("请假流程:1_2")   → Caffeine 查找（JVM 堆内，~0.01ms）
  │   └─ 命中 → 直接返回 ✅
  │
  └─ 2️⃣ l2.get("请假流程:1_2")   → Redis GET cache:retrieval:请假流程:1_2（分布式，~1ms）
      └─ 命中 → l1.put("请假流程:1_2", value) ← 回填 L1（热数据提拔）
              → 返回 ✅
              │
              └─ 未命中 → 执行方法体 → getCachedRetrieval 返回 null
                        → Spring 发现 null，不写入缓存
                        → 返回 null ❌
```

### key 的生成

`@Cacheable` 的 key 通过 SpEL 表达式拼接两个方法参数：

```java
key = "#canonicalQuery + ':' + #deptSuffix"
```

- `canonicalQuery`：规范化后的查询文本（去除语气词、标点，最长 200 字符，超出则 MD5 压缩）
- `deptSuffix`：当前用户可见部门 ID 排序后以 `_` 连接（如 `1_2_3`），实现部门间缓存隔离

同一查询在不同部门维度下产生不同的缓存 key，天然保证权限隔离。

## 四、写缓存流程：putRetrieval("请假流程", "1_2", rankedChunks)

```
RetrievalCacheService.putRetrieval("请假流程", "1_2", rankedChunks)
  │  @CachePut(value = "retrieval_result", key = "#canonicalQuery + ':' + #deptSuffix")
  │
  ▼
[Spring CacheInterceptor（AOP 代理拦截）]
  │  计算 key = "请假流程:1_2"
  │  获取 TwoTierCache("retrieval_result")
  │  调用 cache.put("请假流程:1_2", rankedChunks)
  │
  ▼
TwoTierCache.put("请假流程:1_2", rankedChunks)          ← TwoTierCache.java:91
  │
  ├─ 1️⃣ l1.put("请假流程:1_2", rankedChunks)  → Caffeine 写入（堆内，10min TTL）
  │
  └─ 2️⃣ l2.put("请假流程:1_2", rankedChunks)  → Redis SET cache:retrieval:请假流程:1_2（24h TTL）
```

`@CachePut` 与 `@Cacheable` 的区别：
- **`@Cacheable`**：先查缓存，命中直接返回（不执行方法体）；未命中执行方法体，返回值写入缓存
- **`@CachePut`**：总是执行方法体，然后把返回值写入缓存（用于主动更新缓存）

## 五、淘汰缓存流程：evictAllRetrieval()

```
RetrievalCacheService.evictAllRetrieval()
  │  @CacheEvict(value = "retrieval_result", allEntries = true)
  │
  ▼
[Spring CacheInterceptor]
  │  获取 TwoTierCache("retrieval_result")
  │  调用 cache.clear()  ← 全量清空该缓存区
  │
  ▼
TwoTierCache.clear()
  ├─ l1.clear()  → Caffeine 清空所有 "retrieval_result" 条目
  └─ l2.clear()  → Redis DEL 匹配 cache:retrieval:* 的所有 key
```

文档更新时由 `DocumentUpdateEventListener` 触发，同时全量淘汰 `query_rewrite` 和 `retrieval_result` 两个缓存区。使用 `allEntries = true`（全量淘汰）而非单 key 淘汰，因为文档变更会影响所有相关的检索结果和改写结果。

## 七、缓存配置参数

| 缓存区 | L1 Caffeine | L2 Redis | 用途 |
|--------|-------------|----------|------|
| `query_rewrite` | 最大 1000 条，10min TTL | 1h TTL，Redis key 前缀 `cache:rewrite:` | LLM 查询改写结果缓存（规范化查询 → 改写文本） |
| `retrieval_result` | 最大 1000 条，10min TTL | 24h TTL，Redis key 前缀 `cache:retrieval:` | 检索结果缓存（规范化查询:部门ID → RankedChunk 列表） |

## 八、缓存使用流程

### 正常检索流程（LLM 健康时）

```
用户提问 → ChatController.chat()
           → assistant.chat() → LLM 回答
           → LLM 决定调 KnowledgeRetrievalTool.retrieveKnowledge(query)
             → Step 0: normalize(query) → canonicalKey
             → Step 1: extractDeptSuffix()
             → Step 2: getRewrite(canonicalKey) 查 rewrite 缓存
               ├─ 命中 → 使用缓存改写结果
               └─ 未命中 → LLM 改写 → putRewrite() 写入缓存
             → Step 3: getCachedRetrieval(canonicalKey, deptSuffix) 查检索缓存
               ├─ 命中 → 直接返回（跳过后续全部检索步骤）
               └─ 未命中 → 完整检索管线 → putRetrieval() 写入缓存
           → LLM 结合检索结果生成回答
```

### 熔断降级流程（LLM 异常时）

```
用户提问 → ChatController.chat()
           → @SentinelResource fallback → chatFallback()
             → knowledgeRetrievalTool.retrieveKnowledge(query)
               → 正常走 retrieveKnowledge 内部流程（检索过程仍可命中两级缓存）
             → 返回文档片段供参考
```

> **与旧版的区别**：熔断降级不再单独查询 `qa_answer` 缓存，而是直接调用 `KnowledgeRetrievalTool`，其内部的 `query_rewrite` 和 `retrieval_result` 缓存仍然生效。

### 文档更新时

```
文档变更 → DocumentUpdateEventListener
           → evictAllRewrite()   ← 全量淘汰 query_rewrite 缓存
           → evictAllRetrieval() ← 全量淘汰 retrieval_result 缓存
```

> 由于检索结果和改写结果与文档内容强相关，文档的任何增删改都会导致全量淘汰，确保缓存不会返回基于旧文档的过期内容。
